## Theoretical question and predecessor

The publisher abstract verifies that the authors use prior case evidence from one organization to extend March (1991) with communication technology, knowledge repositories and groupware. The user's explanation specifies Company Z and makes a sharper theoretical reconstruction: IT should be decomposed by *who learns from whom*, the persistence of shared knowledge and whether all members see a common source. March's original model indeed lets individuals learn from the code and lets the code learn from superior individuals, but does **not** let individuals learn directly from each other (March, p. 75). Thus the proposed assumption gap is concrete: indirect, code-mediated diffusion may miss technology-enabled direct and networked learning. The publisher abstract confirms the extension but not every Company Z-to-rule mapping below.

The distinctions `global common / local common / distributed heterogeneous` are **our analytical compression** of the user's reconstruction. They are much more useful for our project than software names. `KRP` is described as filtering, aggregating, storing and diffusing; `TR` localizes learning without enabling every team to reach useful outside knowledge; `ECOP` mixes interest-based, partial communication across formal teams. The open/closed knowledge-transformation-cycle account in the user's explanation predicts why common-source mechanisms exhaust variation while individualized input/output pathways sustain it. That cycle is the proposed mediator chain: `IT structure → information-source diversity/access → knowledge variance → short/long-run learning`. Until the PDF is inspected, do not attribute an exact quotation or page to the authors.

## Experiments: conditional pattern reported in the supplied explanation

The working account says pure `KRP` and `TR` initially raise knowledge quickly but plateau; `ECOP` starts more slowly and eventually overtakes them. Its claimed mechanism diagnostic is knowledge variance: `KRP` collapses it quickly, `ECOP` keeps it positive even late, while `TR` retains mostly *between-team* variance. The interesting consequence is that variance alone is insufficient: retained knowledge must be accessible to learners who can use it. This is a proposed explanation, not a primary-verified numeric finding. Verify the plotted knowledge and variance trajectories, round definitions and whether all runs use the same initial environment.

The supplied account then describes pure (`100/0/0`), augmented (`80/10/10`, `60/20/20`) and blended (`33/33/33`) tool-use mixes. It claims adding external input helps a `TR` core, adding tools to a dominant `KRP` core yields little benefit, and adding homogenizing tools damages a predominantly `ECOP` system. This would show that `A+B` effects depend on the knowledge architecture into which B enters, rather than additive tool benefits. The [author-uploaded ResearchGate record](https://www.researchgate.net/publication/221599333_Information_Technology_and_Organizational_Learning_An_Investigation_of_Exploration_and_Exploitation_Processes) displays captions for combination, learning-rate and turnover tables, confirming those topics exist; it does not expose their cells or justify the numerical values reproduced in the user explanation.

The reported contingencies are substantively important: individual learning rate `p1` allegedly matters little in closed-source systems but faster learning helps `ECOP`, where structure already supplies exploration; turnover allegedly harms `ECOP` because newcomers must rebuild networks while repository/team memory aids assimilation; environmental turbulence allegedly favors `ECOP` because maintained divergent knowledge can become newly useful. These are *conditional mechanism claims to verify against Table 3, result figures and Discussion*, not conclusions to transplant into our manuscript without that check. The supplied `30 replications`, `Round 80`, team/network size and synchronous `t+1` update details require Appendix B or original methods confirmation; the ResearchGate captions independently show Round 80 is one reported comparison horizon.

## What a computational owner should learn and test

The paper's strongest methodological lesson, **as verified at abstract level**, is case evidence → distinct technology mechanisms → extended March model → combination and environment comparisons. The user's reconstruction adds a useful audit checklist: state, source network, decision/update rule, mediator, short versus long outcome, combinations, turnover and turbulence, sensitivity, and update-order artifact. For our ABM, write a corresponding table for `R1` ranking, `R2` explanations and `R3` tasks: exactly which observable information reaches which candidate, when, and whether it changes latent skill or only evidence. A possible new test is feedback-source diversity × candidate response speed, keeping feedback accuracy fixed and logging investment concentration. A falsifier is no interaction or no mediator change after source diversity is varied. **This is an experiment proposal, not an archived simulation result.**
